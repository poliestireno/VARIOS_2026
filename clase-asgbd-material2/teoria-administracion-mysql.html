01

Usuarios: host y ámbito

En MySQL/MariaDB, un usuario no es solo un nombre: es la combinación usuario@host. El mismo nombre de usuario puede existir varias veces con distinto host, y cada combinación es una cuenta independiente con sus propios permisos.

mysql> CREATE USER 'Bego'@'localhost' IDENTIFIED BY 'Beglña';
-- solo puede conectar desde la propia máquina

mysql> CREATE USER 'Mati'@'lasalleinstitucion.es' IDENTIFIED BY 'aMti90';
-- solo puede conectar desde ese dominio concreto

mysql> CREATE USER 'Crispula'@'%' IDENTIFIED BY 'pass';
-- % es un comodín: puede conectar desde cualquier host
02

GRANT y REVOKE

GRANT concede privilegios; REVOKE los retira. Ambos se aplican a un ámbito concreto: toda la instalación (*.*), una base de datos (basedatos.*) o una tabla (basedatos.tabla).

mysql> GRANT SELECT, UPDATE ON red_social.usuario TO 'Bego'@'localhost';

mysql> GRANT DELETE ON red_social.grupo TO 'Mati'@'lasalleinstitucion.es';

mysql> GRANT SELECT, UPDATE, DELETE ON red_social.* TO 'Crispula'@'lasalleinstitucion.es'
    WITH GRANT OPTION;
-- WITH GRANT OPTION: Crispula puede, a su vez, conceder esos mismos permisos a otros

mysql> REVOKE DELETE ON red_social.usuario FROM 'Mifli'@'lasalleinstitucion.es';

mysql> SHOW GRANTS FOR 'Bego'@'localhost';
-- lista los privilegios concedidos a ese usuario

Para dar acceso completo sobre todo el servidor (uso típico de un administrador): GRANT ALL PRIVILEGES ON *.* TO 'admin'@'localhost';

03

La tabla mysql.user y FLUSH PRIVILEGES

Internamente, todos los usuarios y sus permisos viven en las tablas del sistema de la base de datos mysql (sobre todo mysql.user). Es posible editarlas directamente con UPDATE, pero el servidor mantiene esos privilegios cacheados en memoria.

¿Cuándo hace falta FLUSH PRIVILEGES?

GRANT, REVOKE, CREATE USER y DROP USER recargan la caché de privilegios automáticamente. Solo hace falta ejecutar FLUSH PRIVILEGES; a mano cuando se han editado las tablas de permisos directamente con INSERT/UPDATE/DELETE, para forzar al servidor a releer esas tablas.

04

CURRENT_USER() y el fin de PASSWORD()

La función CURRENT_USER() devuelve con qué cuenta (usuario@host) está autenticada la sesión activa — útil para comprobar con qué usuario se ha conectado un script o una sesión de mysql.

mysql> SELECT CURRENT_USER();

La función PASSWORD(), que antes se usaba para cifrar contraseñas a mano, está obsoleta y eliminada en MySQL 8 y versiones recientes de MariaDB. Ya no se puede combinar con GRANT ... IDENTIFIED BY PASSWORD(...). La forma correcta de cambiar una contraseña hoy es:

mysql> ALTER USER 'Mati'@'lasalleinstitucion.es' IDENTIFIED BY 'minuevacontraseña';
05

Los 15 parámetros de ajuste

Configurar un servidor no es solo crear usuarios: hay que ajustar su comportamiento según la carga y las necesidades de cada empresa. Estos son los parámetros más habituales:

  • innodb_buffer_pool_size: memoria reservada para cachear datos e índices de InnoDB en RAM. El parámetro con más impacto en rendimiento de todos.
  • innodb_log_file_size: tamaño de los ficheros de redo log de InnoDB — afecta a cuánto tarda la recuperación tras un fallo y al rendimiento de escritura.
  • max_connections: número máximo de conexiones simultáneas que acepta el servidor.
  • query_cache_size: caché de resultados de consultas repetidas (eliminado en MySQL 8, pero aún presente en MariaDB) — útil solo si hay muchas lecturas idénticas y pocas escrituras.
  • table_open_cache: número de descriptores de tabla que el servidor mantiene abiertos a la vez, para no reabrir archivos constantemente.
  • tmp_table_size / max_heap_table_size: tamaño máximo que puede alcanzar una tabla temporal en memoria antes de volcarse a disco — los dos deben ir a la par.
  • innodb_flush_log_at_trx_commit: compromiso entre durabilidad y velocidad de escritura — 1 es el más seguro (ACID estricto), 0/2 son más rápidos pero arriesgan datos recientes ante un fallo.
  • log_bin: activa el binary log, necesario para replicación y para recuperación punto-en-el-tiempo.
  • slow_query_log / slow_query_log_file: activa el registro de consultas lentas y dónde se guarda ese registro.
  • long_query_time: a partir de cuántos segundos se considera “lenta” una consulta y se anota en el slow query log.
  • bind-address: en qué interfaz de red escucha el servidor — 127.0.0.1 solo acepta conexiones locales, 0.0.0.0 acepta desde cualquier interfaz.
  • innodb_file_per_table: si está activo, cada tabla InnoDB tiene su propio fichero .ibd en vez de compartir un tablespace único — facilita liberar espacio al borrar tablas.
  • performance_schema: activa la instrumentación interna del servidor para monitorizar qué consume tiempo y recursos.
06

Dónde se configuran

Todos estos parámetros se ajustan en el fichero de configuración del servidor, bajo la sección [mysqld]:

  • Debian/Ubuntu: /etc/mysql/mysql.conf.d/mysqld.cnf (o /etc/mysql/my.cnf, que suele incluir al anterior).
  • XAMPP: /opt/lampp/etc/my.cnf.

Tras modificar cualquiera de ellos hace falta reiniciar el servicio (sudo systemctl restart mysql, o sudo /opt/lampp/lampp restart en XAMPP) para que el cambio surta efecto.

Pon esto en práctica en los desafíos RA12_DBA_MYSQL y RA12_USERS_MYSQL, enlazados desde el índice del módulo.
