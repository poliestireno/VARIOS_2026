01

SQL vs. NoSQL

Cuatro puntos que resumen cuándo conviene cada familia:

  • Las bases de datos SQL (MySQL, PostgreSQL) priorizan la integridad y coherencia de los datos.
  • Las bases de datos NoSQL (MongoDB, Cassandra, Redis) priorizan la disponibilidad y la velocidad de crecimiento.
  • NoSQL es mejor cuando hay que manejar volúmenes masivos de datos o la estructura de la información es impredecible.
  • SQL es mejor para aplicaciones con estructuras fijas y acotadas (por ejemplo, el inventario de una tienda local).

Ninguna de las dos familias “gana” en general — la decisión depende de la forma de los datos y de qué se sacrifica: SQL suele sacrificar algo de velocidad de escritura a cambio de garantías fuertes; NoSQL suele sacrificar algo de coherencia inmediata a cambio de escalar horizontalmente sin esfuerzo.

02

Redis, en una frase

Base de datos clave-valor en memoria, extremadamente rápida, pensada sobre todo como caché, almacén de sesiones o cola de mensajes — se desarrolla en detalle en Redis: estructuras de datos en memoria.

03

Cassandra, en una frase

Base de datos distribuida de columna ancha (wide-column store), diseñada por Facebook y cedida a Apache, pensada para escribir grandes volúmenes de datos sin un único punto de fallo: todos los nodos de un clúster Cassandra son iguales entre sí (arquitectura peer-to-peer, sin nodo maestro), y prioriza la disponibilidad frente a la consistencia inmediata (consistencia eventual). Se usa en sistemas que no pueden permitirse caídas, como mensajería a gran escala o series temporales de sensores.

04

DynamoDB, en una frase

Base de datos NoSQL gestionada (clave-valor y documento) de Amazon Web Services — sin servidores que administrar, con escalado automático de capacidad y latencia de un dígito de milisegundo, pensada para aplicaciones serverless donde no se quiere operar la infraestructura de la base de datos.
