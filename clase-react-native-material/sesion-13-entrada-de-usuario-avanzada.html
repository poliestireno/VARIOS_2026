Punto de partida

Hasta ahora habéis mostrado datos: listas, tarjetas, gestos. Hoy la app empieza a recibir datos del usuario. Es un salto real: aparece el teclado en pantalla, que ocupa media pantalla y se abre y cierra en momentos que React Native no controla directamente. Los tres bloques de hoy —TextInput, Modal y KeyboardAvoidingView— son justo las piezas que hacen falta para construir un formulario que funcione bien en un móvil real, no solo en el simulador con el teclado apagado.

1 · TextInput a fondo

TextInput es el único componente de React Native que captura texto escrito. A diferencia de un <input> de HTML, no es un elemento “tonto” que guarda su propio valor: en RN casi siempre lo controlas tú, con estado, exactamente igual que un input controlado en React web.

import { useState } from 'react';
import { TextInput, StyleSheet } from 'react-native';

export default function CampoNombre() {
  const [nombre, setNombre] = useState('');

  return (
    <TextInput
      style={styles.input}
      value={nombre}
      onChangeText={setNombre}
      placeholder="Escribe tu nombre"
    />
  );
}

Cuatro props hacen el 90% del trabajo en clase:

  • value — el texto que se muestra, viene siempre del estado. Sin esto el campo funciona “no controlado” y pierdes el valor cuando quieras leerlo o validarlo.
  • onChangeText — se dispara con cada pulsación, te da directamente el string nuevo (no un evento como en web). onChangeText={setNombre} es un atajo válido porque React ya le pasa ese string como único argumento.
  • keyboardType — cambia el teclado que aparece: "email-address", "numeric", "phone-pad"… No valida nada por sí solo, solo ayuda a escribir más rápido.
  • secureTextEntry — oculta lo escrito con puntos, para contraseñas.
<TextInput
  style={styles.input}
  value={correo}
  onChangeText={setCorreo}
  placeholder="correo@ejemplo.com"
  keyboardType="email-address"
  autoCapitalize="none"
/>

<TextInput
  style={styles.input}
  value={clave}
  onChangeText={setClave}
  placeholder="Contraseña"
  secureTextEntry
/>
keyboardType="numeric" no da un número

onChangeText siempre entrega un string, aunque el teclado sea numérico. Si necesitas el número, conviértelo tú: Number(texto) al usarlo, nunca al guardarlo en el estado del input.

2 · El teclado tapa el formulario

Prueba esto en tu móvil: un formulario con dos o tres campos y un botón “Guardar” al final, en la parte baja de la pantalla. En Android puede que el sistema mueva la pantalla solo; en iOS, casi nunca —el teclado sube por encima de todo y el botón queda tapado detrás de él, inalcanzable. React Native no soluciona esto automáticamente: hay que decírselo explícitamente con KeyboardAvoidingView.

import { KeyboardAvoidingView, Platform, StyleSheet, ScrollView } from 'react-native';

<KeyboardAvoidingView
  style={{ flex: 1 }}
  behavior={Platform.OS === 'ios' ? 'padding' : 'height'}
>
  <ScrollView contentContainerStyle={styles.formulario}>
    {/* tus TextInput y el botón de guardar aquí */}
  </ScrollView>
</KeyboardAvoidingView>

behavior se comporta distinto según la plataforma, por eso se consulta Platform.OS:

  • "padding" (iOS) — añade un relleno inferior del tamaño exacto del teclado, empujando el contenido hacia arriba.
  • "height" (Android) — suele bastar, porque Android ya gestiona parte del ajuste a nivel de sistema. Si tu app en Android usa windowSoftInputMode personalizado, puede necesitar "height" igualmente para casos con ScrollView.

Envolver el formulario en un ScrollView dentro del KeyboardAvoidingView es lo que evita que, en pantallas pequeñas, un campo quede fuera de la vista incluso después de aplicar el ajuste: si no cabe, el usuario puede desplazarse.

Cómo comprobarlo de verdad

Esto solo se ve en un móvil real (o simulador) con el teclado realmente abierto, nunca leyendo el código. Toca un campo, comprueba que el botón de guardar sigue visible y pulsable sin tener que cerrar antes el teclado.

3 · Modal: una pantalla flotante

Modal muestra contenido por encima de todo lo demás, sin necesidad de navegación: ideal para diálogos de confirmación, formularios rápidos de “crear algo nuevo” o detalles que no merecen una pantalla propia en el navegador de la app. Se controla igual que cualquier otro elemento condicional: con un booleano en el estado.

import { useState } from 'react';
import { Modal, View, Text, Pressable, StyleSheet } from 'react-native';

export default function EjemploModal() {
  const [visible, setVisible] = useState(false);

  return (
    <View style={styles.container}>
      <Pressable onPress={() => setVisible(true)}>
        <Text>Abrir formulario</Text>
      </Pressable>

      <Modal
        visible={visible}
        animationType="slide"
        transparent
        onRequestClose={() => setVisible(false)}
      >
        <View style={styles.overlay}>
          <View style={styles.tarjeta}>
            <Text>Contenido del modal</Text>
            <Pressable onPress={() => setVisible(false)}>
              <Text>Cerrar</Text>
            </Pressable>
          </View>
        </View>
      </Modal>
    </View>
  );
}

Tres detalles que marcan la diferencia entre un modal correcto y uno frustrante de usar:

  • transparent deja ver el fondo difuminado/oscurecido detrás; sin él, el modal ocupa toda la pantalla con fondo sólido.
  • onRequestClose es obligatorio en Android: es lo que se dispara con el botón físico/gesto de “atrás”. Si lo omites, ese botón no cerrará el modal.
  • El overlay (la vista exterior, normalmente con justifyContent: 'flex-end' o 'center' y un fondo semitransparente) es lo que te da el efecto de tarjeta flotante —no viene gratis con Modal, lo dibujas tú.

Práctica: nueva nota en un modal

Vais a construir un formulario de “nueva nota” (o “nuevo contacto”, lo que prefiráis) que se abre dentro de un Modal, con un campo de texto obligatorio, validación básica y el teclado bien gestionado con KeyboardAvoidingView.

1

Estado de la lista y del modal

Partid de una lista simple en memoria (con useState) y un booleano para el modal:

const [notas, setNotas] = useState([]);
const [modalVisible, setModalVisible] = useState(false);
const [texto, setTexto] = useState('');
const [error, setError] = useState('');
2

El botón que abre el modal y la lista

Fuera del modal, un Pressable “+ Nueva nota” que hace setModalVisible(true), y debajo una FlatList renderizando notas (repaso de la sesión 11).

3

El formulario dentro del modal

Envuelto en KeyboardAvoidingView, con validación: si el texto está vacío al pulsar “Guardar”, se muestra un mensaje de error en vez de cerrar el modal.

const guardarNota = () => {
  if (texto.trim() === '') {
    setError('Escribe algo antes de guardar');
    return;
  }
  setNotas([...notas, { id: Date.now().toString(), texto }]);
  setTexto('');
  setError('');
  setModalVisible(false);
};

<Modal visible={modalVisible} animationType="slide" transparent
  onRequestClose={() => setModalVisible(false)}>
  <KeyboardAvoidingView
    style={styles.overlay}
    behavior={Platform.OS === 'ios' ? 'padding' : 'height'}
  >
    <View style={styles.tarjeta}>
      <TextInput
        style={styles.input}
        value={texto}
        onChangeText={setTexto}
        placeholder="Escribe tu nota"
      />
      {error !== '' && <Text style={styles.error}>{error}</Text>}
      <Pressable onPress={guardarNota}>
        <Text>Guardar</Text>
      </Pressable>
    </View>
  </KeyboardAvoidingView>
</Modal>
Debería funcionar así

Al tocar el campo de texto, el teclado sube y el botón “Guardar” sigue visible encima de él. Pulsar “Guardar” con el campo vacío muestra el error sin cerrar el modal; con texto, la nota aparece en la lista y el modal se cierra solo.

Reto extra

Añade un segundo campo (por ejemplo “categoría” o “teléfono” si hicisteis contactos) con su propia validación, y un botón “Cancelar” que limpie el formulario y cierre el modal sin guardar nada.
