Arquitectura

Antes de programar a lo loco, hay que sentar las bases: qué pantallas tiene la app, cómo se navega entre ellas y dónde vive cada archivo. Hoy se abre VS Code por primera vez en el proyecto propio, pero solo para montar el esqueleto.

2 horas Sesión 18/24 Primer código del proyecto

Cómo dirigir esta sesión

Cada alumno llega con su propuesta de la sesión 17: nombre, frase, wireframes y funcionalidades mínimas. Hoy esa propuesta se convierte en un proyecto de Expo real, pero todavía sin lógica — solo pantallas vacías conectadas entre sí. El objetivo no es que se vea bonito ni que haga nada; es que la estructura esté bien puesta antes de que empiece a crecer código dentro.

Resiste la tentación de dejar que alguien empiece por la pantalla que más le entusiasma y meta ahí toda la lógica de golpe. Si el esqueleto no está completo y navegable, las siguientes tres sesiones de desarrollo se construyen sobre una base que hay que reordenar a mitad de camino — y eso siempre cuesta más caro que hacerlo bien hoy.

De wireframes a lista de pantallas

El primer paso de cada alumno es aburrido a propósito: contar los wireframes de la sesión 17 y convertir cada uno en una entrada de una lista con su nombre técnico (ListaScreen, DetalleScreen, NuevoScreen…). Después, para cada flecha que conecta dos wireframes, decidir qué tipo de navegación le corresponde — lo que vieron en la sesión 12:

  • Stack cuando una pantalla lleva a otra “hacia dentro” (lista → detalle, lista → formulario nuevo) y hace falta poder volver atrás.
  • Tabs cuando hay 2–4 secciones de igual nivel a las que se salta libremente (por ejemplo “Recetas” y “Favoritos” como pestañas separadas).
  • La combinación más común en estos proyectos: unas tabs por fuera, y dentro de cada tab un stack propio para entrar en el detalle.
Si un alumno duda entre stack y tabs

Pregunta: “¿desde esta pantalla necesitas volver atrás, o simplemente saltar a otra sección?”. Volver atrás es stack. Saltar de sección es tabs. La mayoría de proyectos de este nivel no necesitan más de un nivel de tabs.

Estructura de carpetas recomendada

La misma estructura para todos hace que sea mucho más fácil ayudar a cualquiera en cualquier mesa — sabes dónde mirar sin preguntar. Para un proyecto de este tamaño, esto es suficiente:

mi-app/
  App.js
  screens/
    ListaScreen.js
    DetalleScreen.js
    NuevoScreen.js
  components/
  navigation/
    AppNavigator.js

screens/ tiene una pantalla completa por archivo, una por cada entrada de la lista del paso anterior. components/ se queda vacía por ahora — se va llenando en las sesiones 19 y 20 con piezas que se repiten en más de una pantalla (una tarjeta de item, un botón concreto). navigation/ guarda la configuración de stacks y tabs, separada de App.js para que este quede como un archivo corto que solo arranca la navegación.

Por qué montar el esqueleto antes que la lógica

Un esqueleto es todas las pantallas ya creadas, cada una con un <Text> con su propio nombre, y toda la navegación funcionando entre ellas. Nada más. Se puede tocar cada botón de navegación y comprobar que lleva a donde tiene que llevar, sin que exista todavía ni una lista, ni un formulario, ni un solo dato real.

// screens/ListaScreen.js — así de vacía debe estar hoy
import { View, Text } from 'react-native';

export default function ListaScreen() {
  return (
    <View>
      <Text>Lista</Text>
    </View>
  );
}

Esto vale la pena por dos motivos. Primero, obliga a decidir toda la navegación de golpe, cuando cambiar de opinión todavía es barato — renombrar un archivo vacío cuesta nada; reorganizar un stack con lógica ya metida dentro, cuesta una tarde. Segundo, da a cada alumno una app que ya se puede tocar en el móvil desde el primer día, aunque no haga nada — y eso motiva mucho más que dos sesiones sin ver nada correr.

Práctica de hoy

1

Lista de pantallas y navegación

Cada wireframe de la sesión 17 se convierte en una fila: nombre de pantalla → tipo de navegación que la conecta con las demás (stack, tab, o ambas).

2

Crear el proyecto y la estructura de carpetas

npx create-expo-app con el nombre de su app, y dentro las carpetas screens/, components/ y navigation/ del árbol de arriba.

3

Una pantalla vacía por archivo

Un componente por pantalla, cada uno con un único <Text> con el nombre de la pantalla — ni estilos, ni datos, ni lógica todavía.

4

Montar la navegación completa

Stacks y/o tabs de navigation/AppNavigator.js conectando todas las pantallas, tal como se decidió en el paso 1.

Cómo saber si el esqueleto está listo

Desde el móvil, con Expo Go, se puede llegar a cada una de las pantallas de la propuesta y volver atrás sin que la app se quede colgada ni falte ninguna. Si falta una pantalla del wireframe o sobra una que no estaba planeada, mejor detectarlo hoy que en la sesión 20.
