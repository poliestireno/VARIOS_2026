01

Qué es un repositorio

Git guarda un historial de versiones de un proyecto. Cada commit (confirmación) es una fotografía fija del código en un momento dado, con quién la hizo, cuándo y un mensaje explicando qué cambió. Un repositorio es esa carpeta de proyecto más todo su historial de commits.

Un repositorio puede existir solo en tu ordenador (local) o tener además una copia en un servicio como GitHub (remoto). Lo habitual es tener ambos, y mantenerlos sincronizados: trabajas y confirmas cambios en local, y de vez en cuando los subes al remoto (o bajas los que otra persona haya subido).

El botón + prepara un archivo, el ✓ de Commit lo guarda como un punto fijo del historial local, y Sync intercambia commits con GitHub en ambas direcciones.

02

Clonar un repositorio

Clonar es descargar una copia completa de un repositorio remoto (con todo su historial) a tu ordenador, ya conectada a ese remoto para poder subir y bajar cambios después.

1

Copia la URL del repositorio

En la página del repositorio en GitHub, botón verde Code → pestaña HTTPS → icono de copiar.

2

Clona desde VS Code

Paleta de comandos (Ctrl+Shift+P) → escribe Git: Clone → pega la URL → elige la carpeta local donde guardarlo → cuando termine, pulsa Open en el aviso que aparece.

Si VS Code se abre sin ninguna carpeta, la pantalla de inicio tiene directamente un botón Clone Git Repository… que hace lo mismo.

Primera vez con GitHub en VS Code

Es normal que pida iniciar sesión: botón Sign in with GitHub, autorizar en el navegador que se abre, y volver a VS Code. Con eso queda recordado para siempre en ese ordenador.

03

El panel de Control de código fuente

Es el centro de operaciones de Git en VS Code: icono con forma de rama en la barra lateral, o atajo Ctrl+Shift+G. Ahí aparece una lista de Cambios con todos los archivos que se han modificado desde el último commit, cada uno con una letra:

  • M — Modified: el archivo ya existía y ha cambiado.
  • U — Untracked: archivo nuevo que Git todavía no sigue.
  • D — Deleted: el archivo se ha borrado.

Haz clic en cualquier archivo de la lista para abrir su diff: una vista con lo que había antes a la izquierda y lo que hay ahora a la derecha, en rojo lo eliminado y en verde lo añadido.

En el propio editor

Mientras editas, un archivo con cambios sin guardar en Git muestra una barra de color en el margen izquierdo de cada línea: verde para líneas añadidas, azul para líneas modificadas — sin necesidad de abrir el panel.

04

Guardar cambios: stage y commit

Guardar un cambio en Git son dos pasos. Preparar (stage) es elegir qué cambios van a formar parte del próximo commit — puedes haber tocado tres archivos y querer confirmar solo uno. Confirmar (commit) es lo que realmente crea ese punto fijo en el historial.

1

Prepara los cambios

Pasa el ratón sobre un archivo en la lista de Cambios y pulsa el icono + que aparece a la derecha — se mueve a la sección Cambios preparados. El + de la cabecera de la sección prepara todos los archivos de golpe.

2

Escribe el mensaje y confirma

En el cuadro de texto de la parte superior del panel, describe qué cambia. Después, el botón ✓ Commit (o Ctrl+Enter con el cuadro de texto seleccionado).

Si pulsas Commit sin haber preparado nada, VS Code pregunta si quiere preparar y confirmar todos los cambios a la vez — cómodo cuando el commit va a incluir todo lo que has tocado.

Un buen mensaje de commit

Corto, en presente, y diciendo qué cambia: Añade validación del formulario de login en vez de cambios o arreglos varios. Dentro de unas semanas, ese mensaje es lo único que te va a recordar por qué se hizo el cambio.

05

Subir y bajar cambios: Sync / Push / Pull

Push sube tus commits locales al repositorio remoto. Pull baja al repositorio local los commits que otras personas hayan subido. Sync hace ambas cosas seguidas: primero pull, después push.

En VS Code, el botón está en la barra de estado (abajo, con dos flechas ↑↓ y un número que indica cuántos commits hay pendientes de subir o bajar) y también arriba del panel de Control de código fuente.

Orden recomendado

Pull al empezar a trabajar (para partir de la última versión) y de nuevo justo antes de hacer push, si ha pasado tiempo — evita la mayoría de los conflictos por trabajar sobre una versión desactualizada.

06

Ramas (branches)

Una rama es una línea de trabajo independiente y paralela a la principal (normalmente llamada main), para probar algo o desarrollar una funcionalidad sin tocar el código estable hasta que esté lista.

1

Crea una rama

El nombre de la rama actual aparece siempre en la barra de estado, abajo a la izquierda. Haz clic ahí → Create new branch… → escribe un nombre (por ejemplo formulario-contacto) → Enter. VS Code cambia automáticamente a esa rama nueva.

2

Cambia entre ramas

Mismo sitio, clic en el nombre de la rama → aparece la lista de ramas existentes → selecciona a cuál quieres cambiar.

Cambiar de rama con cambios sin confirmar puede fallar o arrastrarlos a la otra rama — lo más seguro es confirmar (o descartar) antes de cambiar.

07

Fusionar ramas y resolver conflictos

Fusionar (merge) trae los commits de una rama a la rama en la que estás. Desde el panel de Control de código fuente: menú … → Branch → Merge Branch… → elige la rama que quieres traer.

Un conflicto aparece cuando Git no puede decidir solo cómo combinar un cambio — normalmente porque dos ramas modificaron la misma línea de forma distinta. VS Code marca el archivo afectado y, dentro del propio editor, muestra los dos bloques enfrentados con cuatro botones encima:

  • Accept Current Change — se queda con la versión de tu rama actual.
  • Accept Incoming Change — se queda con la versión que viene de la otra rama.
  • Accept Both Changes — conserva las dos, una detrás de otra.
  • Compare Changes — abre un diff lado a lado para decidir con más detalle.

Resuelto el conflicto en todos los archivos afectados, guárdalos, prepáralos con + y confirma el commit — ese commit cierra la fusión.

Si ves <<<<<<< en el archivo

Son los marcadores de conflicto en bruto: todo lo que hay entre <<<<<<< HEAD y ======= es tu versión, y lo que hay entre ======= y >>>>>>> es la entrante. Los botones de VS Code hacen justo eso: borrar lo que sobra y dejar solo el texto final.

08

Historial y comparar cambios

En el explorador de archivos, la sección Timeline (parte inferior del panel lateral, con un archivo abierto) lista sus commits anteriores en orden. Haz clic en cualquiera para ver el diff de ese cambio concreto.

Para un historial más completo — por rama, por autor, en forma de grafo — la extensión GitLens añade una vista de Commit Graph con todo el árbol de commits del repositorio, y anota al lado de cada línea quién la escribió y cuándo (blame en línea).

09

Deshacer cambios

Descartar cambios sin confirmar

Sobre un archivo modificado en la lista de Cambios, el icono de flecha circular (Discard Changes) lo devuelve exactamente a como estaba en el último commit.

Es irreversible

Descartar borra el trabajo sin confirmar para siempre — no hay una papelera de la que recuperarlo. Antes de usarlo, comprueba en el diff que de verdad quieres perder ese cambio.

Deshacer el último commit

Menú … del panel → Commit → Undo Last Commit. El commit desaparece del historial, pero los cambios que contenía vuelven a Cambios preparados — nada se pierde, solo se deshace el punto de confirmación.

10

El archivo .gitignore

Un archivo de texto llamado exactamente .gitignore, en la raíz del proyecto, con un patrón por línea de lo que Git debe ignorar por completo: ni lo rastrea, ni aparece en Cambios, ni se puede subir por accidente.

# dependencias instaladas: se reinstalan con un comando, no hace falta subirlas
node_modules/
vendor/

# configuración local con datos sensibles (contraseñas, claves de API)
.env

# carpeta de salida generada al compilar el proyecto
/dist

# archivos propios de cada sistema operativo
.DS_Store
Solo afecta a partir de ahora

Si un archivo ya se había confirmado antes de añadirlo al .gitignore, Git lo sigue rastreando — el archivo hay que quitarlo aparte. .gitignore solo evita que se empiecen a rastrear archivos nuevos que coincidan con sus patrones.

11

Buenas prácticas

  • Commits pequeños y frecuentes — uno por cada cambio con sentido propio, no uno gigante al final del día.
  • Revisa el diff antes de confirmar — es fácil colar un console.log o un archivo que no tocaba ir.
  • Nunca subas contraseñas, claves de API ni archivos .env — ponlos en .gitignore antes del primer commit del proyecto.
  • Pull antes de empezar a trabajar cada sesión, para partir siempre de la última versión.

Con esto ya se puede trabajar en equipo sobre un mismo repositorio sin pisarse el trabajo. El mensaje de cada commit y la descripción de cada Pull Request son, precisamente, el sitio donde se aplica la sintaxis de Markdown.
