01

La extensión php-redis

$ sudo apt install php-redis -y
$ php -m | grep redis

En instalaciones XAMPP a veces hace falta compilarla a mano contra los binarios de XAMPP si aparece el error “C11 atomic” — parcheando las cabeceras y compilando con phpize + configure --with-php-config=/opt/lampp/bin/php-config + make install, activando después extension=redis.so en php.ini.

02

Conexión y operaciones básicas

$redis = new Redis();
$redis->connect('127.0.0.1', 6379);

$redis->set("clave", "valor");
$redis->setex("clave", 60, "valor"); // con TTL de 60 segundos
echo $redis->get("clave");
$redis->del("clave");
$redis->exists("clave");
03

El patrón caché delante de MySQL

Redis no reemplaza a la base de datos relacional — es una capa de mejora del rendimiento por delante de ella. El flujo básico de lectura:

function obtenerClave($redis, $pdo, $clave) {
  $valor = $redis->get($clave);
  if ($valor !== false) {
    return $valor; // cache hit
  }
  // cache miss: se consulta el origen y se guarda en Redis
  $stmt = $pdo->prepare("SELECT valor FROM datos WHERE clave = ?");
  $stmt->execute([$clave]);
  $valor = $stmt->fetchColumn();
  $redis->set($clave, $valor);
  return $valor;
}

Lo que cambia entre las distintas políticas de reemplazo es cuándo y cómo se invalida o actualiza lo que ya hay en Redis cuando el dato de origen (MySQL) cambia. Trabajar con operaciones de modificación y eliminación de datos exige una estrategia bien definida para mantener la consistencia entre ambos.

04

Actualización inmediata (Write-Through Cache)

Los datos en Redis se actualizan, insertan o borran inmediatamente después de que cambian en MySQL. TTL = infinito.

$pdo->prepare("UPDATE datos SET valor = ? WHERE clave = ?")->execute([$nuevo, $clave]);
$redis->set($clave, $nuevo); // se escribe también en Redis, en el mismo momento

Ventaja: Redis nunca está desactualizado. Coste: cada escritura en MySQL implica también escribir en Redis, aunque esa clave no se vuelva a leer nunca.

05

Invalidación de caché

Cuando se modifican, insertan o eliminan datos en MySQL, la clave correspondiente en Redis simplemente se elimina — Redis cargará los datos actualizados la próxima vez que se consulten (según el patrón de la sección 3). TTL = infinito.

$pdo->prepare("UPDATE datos SET valor = ? WHERE clave = ?")->execute([$nuevo, $clave]);
$redis->del($clave); // no se reescribe, solo se invalida
06

Reemplazo por TTL (Expiración Automática)

Se establece un tiempo de vida para las claves en Redis. Los datos caducan automáticamente pasado ese tiempo y se recargan desde MySQL si se solicitan de nuevo — sin que haga falta ninguna acción explícita al modificar MySQL.

$redis->setex($clave, 60, $valor); // expira solo, a los 60 segundos

Esta es la política usada en la app “Aceitunas” del desafío de RA5+RA6 de ASGBD: TTL distinto según el tipo de clave (10s numéricas, 60s texto).

07

Lazy Loading (Carga Diferida)

Cuando se modifican, insertan o eliminan datos en MySQL, no se realiza ninguna acción inmediata en Redis. Es la propia lectura la que detecta si el dato está desactualizado (comparando Redis contra MySQL) y lo actualiza si hace falta. TTL = infinito.

$valorRedis = $redis->get($clave);
$valorMysql = $pdo->prepare("SELECT valor FROM datos WHERE clave = ?");
$valorMysql->execute([$clave]);
$actual = $valorMysql->fetchColumn();

if ($valorRedis !== $actual) {
  $redis->set($clave, $actual); // se detecta y corrige en el momento de leer
}

A diferencia de la invalidación (sección 5), aquí sí se compara el propio valor en vez de simplemente confiar en que ya no está — el coste se paga en cada lectura, no en cada escritura.

08

Política GilRan (Gilbert Random)

Cada vez que se realiza una consulta en Redis: si la clave no está, se trae de MySQL y se guarda en Redis con TTL infinito. Seguidamente se hace un barrido de todas las claves existentes, y cada una de ellas se borra con un 50% de probabilidad.

foreach ($redis->keys('*') as $k) {
  if (mt_rand(0, 1) === 1) {
    $redis->del($k);
  }
}

Es una política deliberadamente caprichosa — sin garantías de cuánto tiempo vive una clave, útil sobre todo para comparar, en el desafío, contra las cuatro políticas “serias” anteriores y discutir por qué el azar puro no es una buena estrategia de caché en producción.

Pon esto en práctica en RA46_REDIS_CHALLENGE_FASE02: la app “Aceitunas” con TTL, y su extensión con un panel de control web para elegir la política de reemplazo activa.
