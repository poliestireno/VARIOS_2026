Qué es TypeScript, en una frase

TypeScript es JavaScript al que le añades anotaciones de tipo. Un editor con soporte de TypeScript (VS Code lo trae de serie) las lee en tiempo real y te avisa si intentas usar un dato de forma incompatible con su tipo — antes de ejecutar nada. Al construir la app, esas anotaciones se comprueban una última vez y luego se eliminan por completo: en el móvil no corre ni una sola línea de tipos, corre JavaScript normal y corriente.

JavaScript — el error aparece al ejecutar 
function saludar(nombre) {
  return 'Hola, ' + nombre.toUpperCase();
}

saludar(42); // revienta en tiempo de ejecución
// TypeError: nombre.toUpperCase is not a function
TypeScript — el error aparece al escribir 
function saludar(nombre: string) {
  return 'Hola, ' + nombre.toUpperCase();
}

saludar(42); // el editor lo subraya al momento
// Argument of type 'number' is not assignable to parameter of type 'string'

El error de la derecha nunca llega a ejecutarse en el móvil de nadie: lo ves en rojo en VS Code mientras escribes la línea, con el proyecto todavía abierto en tu portátil.

Tipos básicos

La sintaxis es siempre la misma: nombre, dos puntos, tipo. Se anota igual en variables, parámetros de función y propiedades de objeto.

const nombre: string = 'Ana';
const edad: number = 27;
const activo: boolean = true;

const nombres: string[] = ['Ana', 'Luis', 'Marta'];
const edades: number[] = [27, 32, 19];

En la práctica, escribiréis muchas menos anotaciones de las que esperáis. TypeScript infiere el tipo automáticamente a partir del valor inicial, así que esto de aquí ya está completamente tipado sin escribir : string en ningún sitio:

const nombre = 'Ana'; // TypeScript ya sabe que esto es un string
nombre.toUpperCase();  // autocompletado correcto, sin anotar nada
nombre.toFixed(2);   // error: toFixed no existe en un string

La anotación explícita (: string, : number…) hace falta sobre todo cuando no hay un valor inicial del que inferir — el caso más habitual es tipar los parámetros de una función, porque TypeScript no puede adivinar qué le vas a pasar.

Tuplas: arrays de longitud y tipos fijos

Un array normal (string[]) puede tener cualquier longitud. Una tupla fija tanto la longitud como el tipo de cada posición: const punto: [number, number] = [10, 20]. No la usaréis a menudo escribiéndola vosotros, pero es justo la forma que tiene useState de React por dentro: [valor, setValor] es una tupla de dos elementos de tipos distintos, no un array normal.

Tipar funciones

Cada parámetro se tipa por separado, y el retorno se anota después de la lista de parámetros. Retomando la calculadora de IMC de la sesión 1:

function calcularIMC(peso: number, altura: number): number {
  return peso / (altura * altura);
}

calcularIMC(70, 1.75);      // 22.857...
calcularIMC(70, '1.75');   // error: '1.75' no es un number

El : number después del paréntesis de cierre es el tipo de retorno. En la mayoría de casos podéis omitirlo — TypeScript infiere el retorno a partir de lo que hay dentro de la función — pero escribirlo explícitamente es una buena costumbre en funciones que otros compañeros van a usar: documenta la función y, si algún día cambiáis el cuerpo de forma que devuelva otra cosa por error, el editor os avisa inmediatamente.

Con arrow functions la sintaxis es la misma, solo cambia dónde se escribe:

const calcularIMC = (peso: number, altura: number): number => {
  return peso / (altura * altura);
};

Describir objetos: type e interface

Para un objeto con varias propiedades, anotar cada una suelta sería tedioso y no reutilizable. type le pone nombre a una forma, para poder usarla en varios sitios:

type Alumno = {
  nombre: string;
  edad: number;
  aprobado: boolean;
};

const alumno: Alumno = {
  nombre: 'Marta',
  edad: 21,
  aprobado: true,
};

function describir(a: Alumno): string {
  return `${a.nombre} (${a.edad} años)`;
}

Vais a ver interface por todas partes en ejemplos de React, con una sintaxis casi idéntica:

interface Alumno {
  nombre: string;
  edad: number;
  aprobado: boolean;
}

Para lo que vais a necesitar en este curso, son intercambiables — usad type por defecto, es el que veréis más en esta guía, y usad interface si un ejemplo que copiáis de la documentación de una librería ya lo trae así. La diferencia real entre ambos solo importa en proyectos grandes con necesidades avanzadas que no vais a tocar aquí.

Tipos unión y tipos literales

Un tipo unión (con |) dice “esto puede ser de este tipo o de este otro”. Combinado con tipos literales — un texto exacto usado como tipo, no como valor — sirve para modelar algo que solo puede tomar unos pocos valores concretos, en vez de cualquier string:

type Estado = 'pendiente' | 'en curso' | 'terminado';

function marcarTarea(estado: Estado) {
  console.log(`La tarea está: ${estado}`);
}

marcarTarea('en curso');   // bien
marcarTarea('en pausa');   // error: 'en pausa' no es Estado

Esto es mucho más seguro que un string suelto: con string, un typo como 'pendinte' compila sin problema y falla en silencio en tiempo de ejecución; con el tipo Estado, ese mismo typo lo detecta el editor al instante.
