Contexto de la sesión

A estas alturas cada alumno tiene un esqueleto de app navegable, con pantallas construidas en las sesiones 21 y 22. Lo que falta es que esas pantallas muestren datos que valgan la pena: hoy toca decidir de dónde salen. Esta no es una sesión de contenido nuevo para explicar en la pizarra — es una sesión de mesas, donde tu rol es pasar proyecto por proyecto ayudando a decidir la fuente de datos correcta y evitando que nadie se atasque eligiendo entre dos opciones válidas.

El objetivo no es que todos usen lo mismo. Un proyecto de lista de tareas y un proyecto de buscador de películas necesitan cosas completamente distintas, y eso está bien.

El árbol de decisión

Antes de tocar código, cada alumno debería poder responder esta pregunta en una frase: “¿los datos de mi app existen fuera de lo que yo mismo escribo dentro de ella?”

  • No. Todo lo que la app guarda lo generó el propio usuario dentro de la app (una lista de tareas, notas, marcadores, ajustes) y solo le importa a él. → AsyncStorage, ya visto en la sesión 17.
  • Sí. La app necesita datos que existen independientemente del usuario — recetas, libros, películas, resultados de algo — y que no tendría sentido que cada alumno tecleara a mano. → API pública.
  • Las dos cosas. Es habitual y está bien: por ejemplo, la app consulta una API de recetas pero guarda en AsyncStorage cuáles marcó el usuario como favoritas. Son dos problemas distintos, no hace falta resolverlos con la misma herramienta.

AsyncStorage: cuando basta con recordar

Ya se vio en la sesión 17, así que aquí solo hace falta un recordatorio rápido de mesa en mesa: AsyncStorage guarda pares clave–valor como texto (strings) en el propio dispositivo, y sobrevive a cerrar la app. Es la herramienta correcta cuando el dato es del usuario y para el usuario: listas propias, favoritos, configuración, progreso, historial local.

APIs públicas: cuando el dato no es tuyo

Para proyectos que necesiten datos externos, recomienda estas tres APIs gratuitas: no requieren backend propio, tienen buena documentación y responden JSON directo, sin capas raras.

APITemáticaEjemplo de endpoint
TheMealDB Recetas de cocina themealdb.com/api/json/v1/1/search.php?s=pasta
Open Library Libros openlibrary.org/search.json?q=harry+potter
OMDb Películas y series omdbapi.com/?apikey=TU_KEY&s=matrix

TheMealDB y Open Library no piden ni clave ni registro para uso básico — funcionan directo desde el primer fetch. OMDb sí pide una clave gratuita (se consigue en segundos en omdbapi.com/apikey.aspx), pero el límite gratuito es generoso para un proyecto de clase.

Si alguien pide usar otra API que ya conoce

Adelante, no hace falta ceñirse a esta lista. El único filtro real es: gratuita, sin necesidad de montar un backend propio, y que devuelva JSON sin autenticación compleja (OAuth, servidores intermedios). Si cumple eso, sirve igual.

Manejo de errores y estados de carga

Esta es la parte que más se salta la gente cuando trabaja sola, y la que más conviene insistir hoy: una petición de red real puede tardar, puede fallar, y el móvil puede no tener conexión. Un proyecto que solo contempla “todo sale bien” se rompe en cuanto se enseña fuera del aula con mala cobertura.

El patrón mínimo son tres estados: cargando, error y datos listos. Con useState y useEffect es directo:

const [datos, setDatos] = useState<any[] | null>(null);
const [cargando, setCargando] = useState(true);
const [error, setError] = useState<string | null>(null);

useEffect(() => {
  fetch('https://www.themealdb.com/api/json/v1/1/search.php?s=pasta')
    .then((res) => res.json())
    .then((json) => setDatos(json.meals))
    .catch((err) => setError(err.message))
    .finally(() => setCargando(false));
}, []);

Aquí datos queda como any[] a propósito: cada proyecto consulta una API distinta, con una forma de respuesta distinta. En cuanto sepáis qué devuelve la vuestra, define un type propio (como Post en la sesión 16) y sustituid el any[] — el editor os avisará de inmediato de cualquier campo que uséis mal en el renderItem.

Y en el render, cada estado tiene su propia pantalla en vez de dejar hueco en blanco:

if (cargando) {
  return <ActivityIndicator size="large" />;
}

if (error) {
  return <Text>No se pudo cargar: {error}</Text>;
}

return <FlatList data={datos} renderItem={...} />;
Para probarlo de verdad, no de mentira

Pídeles que activen el modo avión un segundo y vuelvan a abrir la pantalla: si la app se queda en blanco o se cierra sola, falta manejar el error. Es la forma más rápida de detectar el problema sin depender de que la API real falle justo en ese momento.

“¿Y si la API tarda mucho?”

Con que exista el estado de carga ya está cubierto lo esencial — el usuario ve un indicador en vez de una pantalla congelada. No hace falta meter un timeout manual para un proyecto de clase; es una mejora opcional, no un requisito de hoy.

Práctica

Cada alumno integra la fuente de datos que decidió (AsyncStorage o una API) en su propio proyecto, con un estado de carga visible en pantalla. Al final de la sesión, cada uno debería poder mostrarte su app con datos reales cargando — y demostrar que no se rompe si desconecta el wifi.
