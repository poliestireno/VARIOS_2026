Punto de partida

Esta es la última sesión del bloque de React Native antes de arrancar el proyecto final. No hay contenido nuevo de verdad: los juegos de clase —Arcanoid, Pang, Black Jack, Brisca— ya usan, cada uno, uno de dos patrones distintos para gestionar su estado. Hoy los ponemos uno al lado del otro, con nombre y con criterio de cuándo usar cada uno, para que la elección deje de ser “lo que hizo el profe en ese ejemplo” y pase a ser una decisión consciente vuestra.

1 · Patrón A: bucle en tiempo real con useRef + tick

Un juego de físicas —una pelota que rebota, una nave que se mueve, colisiones que hay que comprobar 60 veces por segundo— no se puede modelar con useState puro para cada posición: cada setState dispara un re-render de React, y a 60 actualizaciones por segundo eso satura la app en segundos. La solución que ya usasteis en Arcanoid/Pang es esta: el estado real del juego vive en un useRef (que no provoca render al cambiar), y un useState aparte se usa solo como “disparador”, para decirle a React “vuelve a pintar” una vez por frame.

const juego = useRef(crearEstadoInicial(anchoJuego, altoJuego)).current;
const [, setTick] = useState(0);
const redibujar = () => setTick((n) => n + 1);

useEffect(() => {
  const id = setInterval(() => {
    if (juego.estado !== 'jugando') return;
    actualizarFisica(juego, anchoJuego, altoJuego);
    redibujar();
  }, 16);
  return () => clearInterval(id);
}, [anchoJuego, altoJuego]);

Fijaos en cada pieza:

  • useRef(...).current — guarda el objeto juego (posiciones, velocidades, vidas…) en una caja que persiste entre renders pero que React no observa. Mutarlo directamente (juego.pelota.x += 3) no provoca ningún re-render por sí solo.
  • const [, setTick] = useState(0) — el guion antes de la coma descarta el valor, porque nunca se lee: setTick se usa solo por su efecto secundario de forzar un render.
  • setInterval(..., 16) — 16 ms por frame es, aproximadamente, 60 frames por segundo (1000/60 ≈ 16.67). Cada “tick” muta el ref y luego pide un único repintado.
  • La comprobación juego.estado !== 'jugando' es lo que pausa el bucle sin tener que destruir el setInterval: sigue corriendo, pero no hace nada mientras el juego está pausado o terminado.
¿Por qué no useState para la posición de la pelota?

Porque cada setState agenda un render completo del árbol de componentes. A 60 actualizaciones por segundo eso son miles de renders por minuto para un solo valor que cambia constantemente. El ref evita ese coste: React se entera del cambio solo cuando redibujar() lo decide, una vez por frame, sin importar cuántas propiedades del objeto juego hayan mutado mientras tanto.

2 · Patrón B: useState normal por turno

Un juego por turnos —Black Jack, Brisca— es la otra cara de la moneda: no hay nada que actualizar 60 veces por segundo, porque nada cambia hasta que el jugador hace algo. Aquí el patrón de siempre, el que lleváis usando desde la sesión 1, es exactamente el correcto: cada acción del jugador es una llamada a setState, sin bucle de ningún tipo.

const [manoJugador, setManoJugador] = useState<Carta[]>([]);
const [estado, setEstado] = useState<'jugando' | 'ganado' | 'perdido'>('jugando');

const pedirCarta = () => {
  if (estado !== 'jugando') return;
  const nuevaMano = [...manoJugador, baraja.current.pop()];
  setManoJugador(nuevaMano);
  if (calcularTotal(nuevaMano) > 21) {
    setEstado('perdido');
  }
};

Nada de setInterval, nada de useRef para el estado del juego: pedirCarta se ejecuta una vez, cuando el jugador toca el botón, y ese único setState (o dos, como aquí) es exactamente el coste de renders que hace falta —ni uno más. Fijaos que baraja sí es un useRef: la baraja de cartas mutable (sacar cartas de un mazo) no necesita disparar renders por sí sola, solo el resultado visible (la mano) lo necesita.

useState<'jugando' | 'ganado' | 'perdido'>(...) es una unión de literales, de la sesión de TypeScript: estado solo puede valer una de esas tres cadenas exactas —si en algún setEstado escribes 'perdio' por error, el editor te lo marca antes de probarlo en el móvil.

3 · Cuándo usar cada uno

  • Patrón A (ref + tick) cuando hay animación o físicas continuas: algo se mueve, cae, rebota o se comprueba colisión frame a frame, sin que el usuario tenga que tocar nada para que cambie.
  • Patrón B (useState normal) cuando el estado solo cambia en respuesta a una acción puntual del usuario: pulsar “pedir carta”, jugar una ficha, tocar un botón. Un render por acción es barato y perfectamente razonable.
  • Ambos pueden convivir en el mismo juego: un marcador de puntos por turno (patrón B) encima de un tablero con físicas en tiempo real (patrón A) es perfectamente normal —lo que importa es no usar B donde hace falta A (rendimiento) ni A donde basta con B (complejidad innecesaria).

Práctica: añade una función a tu juego

Elegid uno de los cuatro juegos ya vistos en clase —Arcanoid, Pang, Black Jack o Brisca— y añadidle una función nueva de vuestra elección. El objetivo de hoy no es el resultado visual: es que identifiquéis con seguridad qué patrón de estado usa el juego que elegisteis, y por qué es el correcto para ese caso.

1

Identificad el patrón antes de tocar código

Abrid el juego elegido y localizad: ¿hay un setInterval y un useRef con el estado del juego (patrón A), o solo useState disparado por onPress (patrón B)? Escribidlo en una línea antes de seguir.

2

Elegid una función nueva

Algunas ideas, de menor a mayor complejidad:

  • Marcador de mejor puntuación con AsyncStorage (sesión 17): guardar y mostrar el récord entre partidas.
  • Botón de pausa: en patrón A, cambia juego.estado a 'pausado' para que el bucle deje de actualizar física sin destruirlo; en patrón B, simplemente deshabilita los botones de acción.
  • Modo “difícil”: parámetros distintos (más velocidad en patrón A, reglas más estrictas en patrón B) seleccionables antes de empezar.
  • Contador de partidas jugadas: un useState simple que suma uno cada vez que el juego termina, con o sin persistencia.
3

Implementadla respetando el patrón existente

Si el juego usa patrón A, vuestra función nueva no debería añadir un useState que cambie 60 veces por segundo; si usa patrón B, no deberíais necesitar meter un setInterval para nada de esto.

Lo que de verdad se evalúa hoy

No la vistosidad del resultado, sino que podáis explicar en voz alta: “mi juego usa el patrón X porque Y”, y que la función que añadisteis encaje en ese mismo patrón sin forzar nada.

Reto extra

Si vuestro juego es de patrón B (Black Jack, Brisca), pensad —sin necesariamente implementarlo— qué parte de un futuro añadido sí necesitaría patrón A: por ejemplo, una animación de la carta deslizándose hasta la mano. No hace falta programarlo, solo identificar dónde cambiaría el patrón y por qué.
