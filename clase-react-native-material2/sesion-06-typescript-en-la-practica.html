Propiedades opcionales

No todos los objetos de una misma forma tienen siempre todos los datos rellenos. Un ? después del nombre de la propiedad dice “esto puede no estar”:

type Alumno = {
  nombre: string;
  edad: number;
  email?: string; // puede no venir
};

const a: Alumno = { nombre: 'Ana', edad: 27 }; // válido, sin email

function contactar(a: Alumno) {
  console.log(a.email.toUpperCase()); // error: 'email' puede ser undefined
}

Ese error es justo el motivo por el que la propiedad opcional merece la pena: TypeScript os obliga a comprobar que el dato existe antes de usarlo, con un if o con el operador ?. (optional chaining) que ya usasteis en JavaScript:

function contactar(a: Alumno) {
  console.log(a.email?.toUpperCase() ?? 'sin email');
}

El readonly es el otro modificador habitual: marca una propiedad que se puede leer pero no reasignar después de creado el objeto, útil para datos que no deberían cambiar por accidente (un id, por ejemplo).

type Alumno = {
  readonly id: string;
  nombre: string;
};

const a: Alumno = { id: 'a1', nombre: 'Ana' };
a.nombre = 'Ana María'; // bien
a.id = 'a2';            // error: id es readonly

any frente a unknown

any apaga TypeScript por completo para ese valor: podéis hacer lo que sea con él sin que el editor proteste nunca, lo cual anula justo lo que veníais buscando. Aparece solo, sin que lo pidáis, en un sitio muy concreto: el resultado de JSON.parse() o de .json() tras un fetch, porque TypeScript no tiene forma de saber qué forma tiene un texto JSON hasta que lo leéis.

const datos: any = JSON.parse('{"nombre": "Ana"}');
console.log(datos.nombre.aFuncionQueNoExiste()); // compila sin avisar, revienta al ejecutar

unknown es la alternativa más segura para “no sé qué es esto todavía”: acepta cualquier valor igual que any, pero no os deja usarlo hasta que comprobéis (o afirméis) de qué tipo es en realidad.

const datos: unknown = JSON.parse('{"nombre": "Ana"}');
console.log(datos.nombre); // error: no puedes leer propiedades de 'unknown' sin comprobar antes

if (typeof datos === 'object' && datos !== null && 'nombre' in datos) {
  console.log((datos as { nombre: string }).nombre); // bien, ya comprobado
}

En la práctica, para los datos de una API en la que confiáis (como en la sesión 4), la solución habitual es más directa: en vez de comprobar la forma a mano, definís el type que esperáis y le decís a TypeScript “confía en mí, esto tiene esta forma” con as:

type Post = { userId: number; id: number; title: string; body: string };

async function obtenerPost(id: number): Promise<Post> {
  const respuesta = await fetch(`https://jsonplaceholder.typicode.com/posts/${id}`);
  const datos = await respuesta.json() as Post;
  return datos;
}
“as Post” es una promesa, no una comprobación

as Post no valida nada en tiempo de ejecución — solo le dice al editor “trátalo como si fuera esto”. Si la API cambia de forma sin avisar, as no os va a salvar; solo os da autocompletado y avisos correctos mientras la API responde lo que esperáis. Es una herramienta de productividad, no una red de seguridad contra datos corruptos.

Genéricos, lo justo para reconocer useState<T>

Un genérico es un tipo que recibe otro tipo como parámetro, escrito entre <>. No hace falta que sepáis crear vuestros propios genéricos para este curso — sí que sepáis leerlos, porque los vais a ver constantemente a partir de la semana que viene:

function primero<T>(lista: T[]): T {
  return lista[0];
}

primero([1, 2, 3]);         // T = number, devuelve un number
primero(['a', 'b']);      // T = string, devuelve un string

T es un marcador de posición: se rellena con el tipo real cada vez que llamáis a la función, y TypeScript lo infiere solo a partir de lo que le pasáis — no tenéis que escribirlo casi nunca. Esto es exactamente lo que pasa con useState<number>(0) que veréis en la guía del contador: useState es una función genérica, y <number> es vosotros rellenando T a mano en vez de dejar que lo infiera, porque a partir de un array vacío (useState([])) no hay nada de lo que inferir.

Adelanto: tipar props de un componente

Todavía no habéis escrito JSX — eso empieza en la sesión 7 — pero la pieza de TypeScript que más vais a usar en React es tan sencilla como lo de hoy: un type para describir qué recibe un componente, usado como tipo de su único parámetro (las props):

type TarjetaPerfilProps = {
  nombre: string;
  edad: number;
  verificado?: boolean; // opcional, como antes
};

function TarjetaPerfil({ nombre, edad, verificado }: TarjetaPerfilProps) {
  // aquí ya sabéis, sin adivinar, que "edad" es number y "nombre" un string
  return `${nombre} (${edad})${verificado ? ' ✓' : ''}`;
}

Nada de esto es nuevo: es exactamente un type con propiedades, algunas opcionales, usado para tipar el parámetro de una función — solo que ese parámetro se llama “props” y esa función va a devolver JSX en vez de un string. La sesión que viene retomamos justo aquí.
