Contexto de la sesión

Después de conectar datos en la sesión 23, es habitual que aparezca un problema nuevo: varias pantallas necesitan el mismo dato. La lista de favoritos se marca en una pantalla, pero hay que mostrarla en otra, y quizás también en una tercera. Esta sesión tiene dos partes bien diferenciadas: primero, quien lo necesite aprende a resolver ese problema con Context API; segundo, todo el mundo — lo necesite o no — repasa una checklist funcional antes de pasar a pulir lo visual en la sesión 25.

El problema: prop drilling

Imagina un proyecto con esta estructura: una pantalla Lista donde se marca algo como favorito, una pantalla Detalle que también permite marcarlo, y una pantalla Favoritos que muestra todos los marcados. Las tres necesitan leer y modificar la misma lista de favoritos.

La solución ingenua es guardar esa lista en el componente más alto (por ejemplo App) y pasarla como prop hacia abajo, pantalla por pantalla, hasta llegar a donde se usa. El problema es que si Favoritos está tres o cuatro niveles por debajo de donde vive el estado, cada componente intermedio tiene que recibir y reenviar esa prop aunque no le importe en absoluto — solo la está pasando de largo. A eso se le llama prop drilling, y cuanto más crece el proyecto, más frágil se vuelve: mover una pantalla de sitio rompe la cadena de props sin que el error sea obvio.

La solución: Context API

Context permite que cualquier componente lea (o modifique) un valor compartido directamente, sin que nadie tenga que pasárselo a mano por en medio. Son tres piezas:

  • createContext() crea el “canal” compartido.
  • Un Provider envuelve la parte de la app que necesita acceso, y le da el valor real.
  • useContext() lo lee desde cualquier componente dentro de ese Provider, sin importar cuántos niveles de profundidad haya.
1

Crea el contexto de favoritos

En un archivo nuevo, por ejemplo context/FavoritosContext.tsx — fuera de app/, porque no es una pantalla:

import { createContext, useContext, useState } from 'react';

type Item = { id: string; nombre: string };

type FavoritosContextType = {
  favoritos: Item[];
  agregarFavorito: (item: Item) => void;
  quitarFavorito: (id: string) => void;
};

const FavoritosContext = createContext<FavoritosContextType | undefined>(undefined);

export function FavoritosProvider({ children }: { children: React.ReactNode }) {
  const [favoritos, setFavoritos] = useState<Item[]>([]);

  const agregarFavorito = (item: Item) => {
    setFavoritos((prev) => [...prev, item]);
  };

  const quitarFavorito = (id: string) => {
    setFavoritos((prev) => prev.filter((f) => f.id !== id));
  };

  return (
    <FavoritosContext.Provider value={{ favoritos, agregarFavorito, quitarFavorito }}>
      {children}
    </FavoritosContext.Provider>
  );
}

export function useFavoritos() {
  const ctx = useContext(FavoritosContext);
  if (!ctx) throw new Error('useFavoritos debe usarse dentro de FavoritosProvider');
  return ctx;
}

El estado real (useState) vive dentro del Provider, en un solo sitio. El tipo FavoritosContextType es lo que gana TypeScript aquí: en cualquier pantalla que use useFavoritos(), el editor ya sabe que favoritos es un array de Item y que agregarFavorito espera exactamente uno — sin tipo, cualquier undefined del contexto pasaría desapercibido hasta reventar en tiempo de ejecución.

2

Envuelve la app con el Provider

En app/_layout.tsx, el layout raíz por el que pasan todas las rutas:

import { Stack } from 'expo-router';
import { FavoritosProvider } from '../context/FavoritosContext';

export default function RootLayout() {
  return (
    <FavoritosProvider>
      <Stack />
    </FavoritosProvider>
  );
}

Cualquier pantalla dentro de app/ se renderiza a través de este Stack, así que todas quedan automáticamente dentro del Provider y pueden acceder a los favoritos — sin importar en qué carpeta o grupo de rutas vivan.

3

Úsalo desde cualquier pantalla

Sin pasar ni una sola prop de por medio, y sin necesitar el objeto completo por parámetro de ruta — solo el id:

import { useLocalSearchParams } from 'expo-router';
import { Pressable, Text } from 'react-native';
import { useFavoritos } from '../../context/FavoritosContext';
import { items } from '../../data/items';

export default function PantallaDetalle() {
  const { favoritos, agregarFavorito } = useFavoritos();
  const { id } = useLocalSearchParams<{ id: string }>();
  const item = items.find((i) => i.id === id)!;

  return (
    <Pressable onPress={() => agregarFavorito(item)}>
      <Text>Marcar como favorito</Text>
    </Pressable>
  );
}
Cómo saber si funcionó

Marca un favorito desde la pantalla de detalle y navega a la pantalla de favoritos: debería aparecer ahí sin que hayas tocado ninguna prop de navegación para pasarlo. Si no aparece, revisa que la pantalla esté realmente dentro del FavoritosProvider, es decir, que app/_layout.tsx la envuelva.

¿Y si el proyecto de alguien no tiene este problema?

Perfecto, no hace falta forzar un Context donde no hace falta. Si cada pantalla del proyecto trabaja con sus propios datos y ninguna necesita algo que otra pantalla tiene, useState local en cada pantalla sigue siendo la opción correcta. Context resuelve un problema concreto (dato compartido entre pantallas), no es un paso obligatorio de todo proyecto.

Checklist funcional antes de pulir lo visual

Independientemente de si un proyecto necesitó Context o no, todos deberían pasar por esta checklist antes de la sesión 25. Es la última oportunidad cómoda para arreglar comportamiento antes de que la atención se vaya a colores y tipografías.

  • ¿Maneja listas vacías? Si un usuario nuevo abre la app y no tiene favoritos, resultados o tareas todavía, ¿ve un mensaje razonable o una pantalla en blanco que parece rota?
  • ¿Hay algún crash conocido? Cualquier acción que rompa la app (tocar dos veces seguidas un botón, volver atrás en medio de una carga, dejar un campo vacío) tiene que arreglarse ahora, no maquillarse después.
  • ¿Los datos persisten o se pierden al cerrar la app? Si el proyecto usa AsyncStorage, cerrar del todo la app (no solo minimizarla) y reabrirla no debería borrar nada.
  • ¿Todos los botones hacen algo? Vale la pena tocar cada botón y cada enlace de navegación una vez, en orden, buscando algo que quedó a medio conectar.

Práctica

Cada alumno identifica primero si su proyecto tiene datos que varias pantallas necesitan compartir. Si es así, los mueve a un Context siguiendo el patrón de esta sesión. Si no es el caso, dedica el resto de la sesión a corregir los puntos de la checklist funcional. Al terminar, cada proyecto debería sobrevivir a un repaso rápido: abrir todas las pantallas, tocar todos los botones, cerrar y reabrir la app.
