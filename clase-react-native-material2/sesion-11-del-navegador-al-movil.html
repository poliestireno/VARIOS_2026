Expo: la capa que te ahorra Xcode y Android Studio

React Native, usado a pelo, exige herramientas nativas pesadas: Android Studio (varios gigas, con su propio SDK y emuladores) para compilar para Android, y un Mac con Xcode para compilar para iOS. Si el objetivo fuera solo aprender a construir interfaces con componentes, ese peaje de instalación no aporta nada — y en un aula donde cada alumno trae un portátil distinto, sería la clase entera perdida en instaladores.

Expo es un conjunto de herramientas construido encima de React Native que se salta ese paso. Te da un proyecto ya configurado, un servidor de desarrollo, y una forma de ejecutar tu app en un móvil real sin compilar nada nativo en tu portátil. Tú escribes JavaScript y JSX; Expo se encarga de empaquetarlo y servirlo. A cambio, no puedes instalar cualquier librería nativa exótica sin pasos extra — pero para prácticamente todo lo que vamos a construir en este curso, sobra de largo.

Expo Go: la app que ejecuta tu código sin instalarlo

Expo Go es una app normal, ya publicada en Play Store y App Store, que sabe descargar y ejecutar el JavaScript de tu proyecto sobre la marcha. Cuando lanzas npm start y escaneas el QR con el móvil, tu teléfono no instala tu app: descarga tu código JS y lo corre dentro de Expo Go, que ya trae compilados los bloques nativos que vas a usar (View, Text, Image…). Es parecido a abrir una página web, solo que en vez de pintar HTML, pinta componentes nativos de verdad.

Esto es justo lo que hace posible el Fast Refresh: guardas un cambio en VS Code, el móvil recibe el JS actualizado y se refresca solo, sin recompilar nada nativo ni volver a escanear el QR.

Un límite honesto

Si algún día una app necesita una librería nativa que Expo Go no trae de fábrica, hace falta generar un “development build” propio. Es un escalón más avanzado que queda fuera de este curso — con lo que trae Expo Go de serie llegamos perfectamente hasta el final.

Cómo se organiza un proyecto Expo

Al crear un proyecto con create-expo-app obtienes ya un proyecto en TypeScript, con la navegación resuelta por archivos (Expo Router). Tras limpiar la plantilla de ejemplo con npm run reset-project (como en la guía “Contador en Expo”), estos son los archivos que realmente importan:

mi-primera-app/
├── app/
│   ├── _layout.tsx    ← layout raíz: envuelve todas las pantallas
│   └── index.tsx      ← la pantalla de la ruta "/", tu punto de partida
├── app.json           ← nombre, icono, orientación de la app
├── package.json        ← dependencias y scripts, como en cualquier proyecto Node
├── tsconfig.json       ← configuración de TypeScript
├── assets/             ← imágenes e iconos que se empaquetan con la app
│   └── images/
└── node_modules/

Cada archivo dentro de app/ es una pantalla: su nombre define la ruta. index.tsx exporta por defecto el componente que se ve en la ruta raíz — es prácticamente el único archivo que vas a tocar en las próximas sesiones, hasta que lleguemos a Navegación y empecemos a añadir pantallas nuevas como archivos. _layout.tsx es el envoltorio común a todas las pantallas (por ahora, uno mínimo con un Stack de Expo Router; no hace falta tocarlo todavía). package.json es exactamente lo que ya conoces de React web: dependencias y comandos (npm start, etc). La carpeta assets/ es nueva: ahí van las imágenes que tu app necesita llevar consigo, y las vas a usar en la Sesión 12.

Las tres cosas que más chocan viniendo de la web

1. View en vez de div. No hay HTML en React Native — no hay DOM, ni navegador debajo. View es el contenedor universal, el equivalente a un div, pero solo entiende un objeto de estilos, nunca clases CSS.

React (web) 
<div className="tarjeta">
  ...
</div>
React Native 
<View style={styles.tarjeta}>
  ...
</View>

2. Text es obligatorio para todo texto. En la web puedes soltar texto suelto dentro de casi cualquier elemento. En React Native, un texto que no está envuelto en <Text> directamente revienta la app — no hay forma de renderizar un carácter sin él.

✗ En React Native, esto falla 
<View>
  Hola mundo
</View>
✓ Así sí funciona 
<View>
  <Text>Hola mundo</Text>
</View>

3. StyleSheet en vez de CSS. No hay hojas de estilo, ni selectores, ni cascada, ni herencia entre elementos. Los estilos son objetos de JavaScript: las propiedades van en camelCase y los tamaños son números simples (dp, “density-independent pixels”), nunca cadenas con px.

React (web) — CSS 
.tarjeta {
  background-color: #fff;
  padding: 16px;
  border-radius: 8px;
}
React Native — StyleSheet 
const styles = StyleSheet.create({
  tarjeta: {
    backgroundColor: '#fff',
    padding: 16,
    borderRadius: 8,
  },
});

StyleSheet.create valida y optimiza ese objeto internamente, pero conceptualmente sigue siendo un objeto JS normal — nada de cascada: si quieres que un texto dentro de una View sea blanco, se lo tienes que decir a ese Text en concreto, ningún estilo “baja” solo.

El mismo ciclo de render, un destino distinto

En la Sesión 7 vimos el ciclo de render de React: primer render, commit, esperar, cambiar estado, re-render, reconciliación, commit otra vez. Ese ciclo no cambia nada en React Native — sigue siendo el mismo motor de React ejecutando el mismo JavaScript. Lo único que cambia son los pasos 3 y 8: dónde termina yendo a parar el resultado.

1Primer render

Igual que en la web: React ejecuta tu función componente de arriba a abajo.

↓
2Construye el árbol de elementos

El árbol describe <View>, <Text>, <Pressable>… en vez de <div>, <span>, <button>. No hay HTML detrás.

↓
3Commit inicial — aquí está la diferencia

No hay DOM que pintar. React Native envía esa descripción al lado nativo, que crea vistas nativas reales: UIView en iOS, android.view.View en Android.

↓
4Esperando…

Igual que en la web, pero los eventos son táctiles: un toque, un swipe, un teclado nativo — no un clic de ratón.

↓
5Algo cambia el estado

setAlgo(...) funciona exactamente igual que en React web — es el mismo hook useState.

↓
6Re-render

React vuelve a ejecutar tu componente con el nuevo valor de estado. Mismo motor, mismo JavaScript.

↓
7Reconciliación (diffing)

Se compara el árbol nuevo con el anterior para calcular exactamente qué cambió.

↓
8Commit — otra vez la diferencia

Solo ese cambio se envía al lado nativo, que actualiza las vistas reales en pantalla — sin volver a crearlas todas.

Vuelve al paso 4 y espera el siguiente toque de pantalla.
“El puente” en una frase

Tu código JavaScript corre en su propio hilo, calculando qué debería cambiar. Ese resultado cruza hacia el lado nativo, que es quien de verdad dibuja píxeles en pantalla. React DOM cruza ese puente hacia el navegador; React Native lo cruza hacia iOS o Android — es la misma idea de “calcular aquí, pintar allá” en los dos casos.

Práctica

Hoy la parte práctica no va en esta página: hay una guía completa, paso a paso, que cubre desde crear el proyecto hasta tener un contador funcionando en tu propio móvil. Ábrela ahora y síguela de principio a fin.

Guía completa: Contador en Expo

Sigue todos los pasos en la guía del contador — crea el proyecto, ábrelo en VS Code, arráncalo y escanéalo con tu móvil, y construye el contador con useState, View, Text y Pressable aplicando justo lo que hemos visto hoy.

Cuando tengas el contador funcionando y tocando la pantalla del móvil de verdad, prueba estos dos retos extra:

  • Reto 1: añade un segundo Pressable con el texto “Restar 1” que nunca baje del cero (pista: Math.max(0, contador - 1)).
  • Reto 2: añade un tercer Text debajo del número que muestre “Es par” o “Es impar” según el valor de contador.
Tres ejemplos completos más para practicar

Adivina el número: un juego con TextInput, pistas de “mayor”/“menor” y conteo de intentos — buen siguiente paso justo después del contador.

Cursor de 4 direcciones: cuatro botones en cruz que muestran en grande la última dirección pulsada — útil para ver useState con un tipo cerrado de valores y renderizado condicional.

Login + tabla aleatoria: ya con dos pantallas y navegación real (expo-router) — un formulario de login que, si usuario/contraseña son a1/a1, lleva a una segunda pantalla con una tabla 3x3 de números aleatorios.

Todos son el contenido completo de sus archivos app/*.tsx, comentados línea a línea: se abren para leerlos directamente, con un botón para copiar el código y pegarlo en tu propio proyecto.
