Navegación

Hasta ahora, cada app ha vivido en una sola pantalla. Hoy es donde empiezan a parecerse a las apps de verdad: varias pantallas conectadas, con datos que viajan de una a otra, y una barra de pestañas para las secciones principales.

Qué vas a ver hoy

Expo Router: la navegación ya viene resuelta

En React Navigation “clásico” tenías que instalar la librería y describir a mano cada navegador (createStackNavigator, createBottomTabNavigator…). Expo Router — ya incluido en tu proyecto desde que lo creaste con create-expo-app — hace lo mismo por convención de archivos: cada archivo .tsx dentro de app/ es una pantalla, y la carpeta donde vive define su ruta. No hay nada que instalar ni ningún NavigationContainer que envolver a mano: cada _layout.tsx declara qué tipo de navegador gobierna esa carpeta.

app/
├── _layout.tsx                 ← Stack raíz
└── (tabs)/
    ├── _layout.tsx             ← Tabs: Productos y Ajustes
    ├── ajustes.tsx             ← pantalla "Ajustes"
    └── productos/
        ├── _layout.tsx         ← Stack de esta pestaña
        ├── index.tsx           ← lista, ruta /productos
        └── [id].tsx            ← detalle, ruta /productos/:id

Los paréntesis en (tabs) son una carpeta “de agrupación”: organiza archivos sin aparecer en la URL. Los corchetes en [id].tsx marcan un segmento dinámico: captura cualquier valor en esa posición de la ruta.

Stack por carpeta: pantallas apiladas

Un Stack mantiene las pantallas en una pila: cada vez que navegas “hacia delante”, apila una pantalla nueva encima; al volver atrás (con el gesto del sistema o el botón de la cabecera), la desapila. Es el patrón natural para flujos tipo “lista → detalle”, y en Expo Router se declara con un _layout.tsx dentro de la carpeta que quieres apilar:

// app/(tabs)/productos/_layout.tsx
import { Stack } from 'expo-router';

export default function ProductosLayout() {
  return <Stack />;
}

Con eso, index.tsx y [id].tsx dentro de esa misma carpeta pasan a ser automáticamente “lista” y “detalle” de un mismo Stack, con cabecera y gesto de volver incluidos, sin registrar nada más.

Navegar y leer el parámetro de la URL

Desde la lista, un Link hacia /productos/${item.id} hace la navegación; con asChild, el componente hijo (aquí un Pressable) recibe el comportamiento de enlace sin que Link añada su propia envoltura visual:

// app/(tabs)/productos/index.tsx
import { Link } from 'expo-router';
import { FlatList, Pressable, Text } from 'react-native';
import { productos } from '../../../data/productos';

export default function ListaProductos() {
  return (
    <FlatList
      data={productos}
      keyExtractor={(item) => item.id}
      renderItem={({ item }) => (
        <Link href={`/productos/${item.id}`} asChild>
          <Pressable>
            <Text>{item.nombre}</Text>
          </Pressable>
        </Link>
      )}
    />
  );
}

Y en [id].tsx, el segmento dinámico llega con useLocalSearchParams. Fíjate en un matiz importante frente a React Navigation: por la URL solo viajan valores serializables (texto), nunca un objeto completo — así que aquí pasamos el id y buscamos el producto entero en el destino:

// app/(tabs)/productos/[id].tsx
import { useLocalSearchParams } from 'expo-router';
import { Text, View } from 'react-native';
import { productos } from '../../../data/productos';

export default function DetalleProducto() {
  const { id } = useLocalSearchParams<{ id: string }>();
  const producto = productos.find((p) => p.id === id);

  return (
    <View style={styles.contenedor}>
      <Text style={styles.titulo}>{producto?.nombre}</Text>
      <Text style={styles.precio}>{producto?.precio} €</Text>
    </View>
  );
}

useLocalSearchParams<{ id: string }>() le dice a TypeScript qué forma tienen los parámetros de esta ruta — sin ese tipo, id quedaría como string | string[] (la URL podría en teoría repetir el segmento) y el editor te obligaría a comprobarlo en cada uso.

Tabs: pestañas para secciones, no para flujos

Un Tabs muestra varias pantallas como pestañas fijas (normalmente abajo), todas accesibles en cualquier momento con un toque, sin noción de “apilar” ni de “volver atrás”. Úsalo para las secciones principales de la app — sitios a los que el usuario vuelve constantemente— y reserva el Stack para flujos de profundización dentro de cada sección (una lista que lleva a un detalle, un detalle que lleva a un formulario, etc). Se declara igual que el Stack: con un _layout.tsx, esta vez en la carpeta (tabs):

// app/(tabs)/_layout.tsx
import { Tabs } from 'expo-router';

export default function TabsLayout() {
  return (
    <Tabs>
      <Tabs.Screen name="productos" options={{ title: 'Productos' }} />
      <Tabs.Screen name="ajustes" options={{ title: 'Ajustes' }} />
    </Tabs>
  );
}

Fíjate en algo importante: la pestaña “productos” no apunta a un archivo suelto, sino a la carpeta productos/ — con su propio _layout.tsx con un Stack, que vimos arriba. Esto es anidar navegadores: un Tabs por fuera, con un Stack dentro de una de sus pestañas, exactamente igual de compuesto que en React Navigation clásico, solo que la jerarquía de carpetas hace las veces de código de configuración. Así, dentro de “Productos” puedes navegar de la lista al detalle con normalidad, mientras la barra de pestañas de abajo sigue siempre visible.

Tabs vs Stack, en una frase

Si el usuario necesita volver a ese sitio constantemente, es una pestaña. Si es un paso dentro de una tarea que empieza en otro sitio y a la que no se vuelve directamente, es una pantalla en un Stack.

Práctica

Construye una app de 3 pantallas combinando lo de hoy:

1

Lista de productos (app/(tabs)/productos/index.tsx)

Un array tipado de al menos 10 productos (id, nombre, precio, y opcionalmente una imagen), mostrados con FlatList. Cada fila, al tocarla, navega a /productos/${item.id} con un Link.

2

Detalle de producto (app/(tabs)/productos/[id].tsx)

Lee el id con useLocalSearchParams, busca el producto en el array y muestra su nombre, precio y demás datos, con su propio estilo vía StyleSheet. Comprueba que el botón de volver de la cabecera (o el gesto de deslizar desde el borde) te devuelve a la lista — te lo da gratis el _layout.tsx con Stack de esa carpeta.

3

Ajustes (app/(tabs)/ajustes.tsx)

Una tercera pantalla simple, accesible desde una segunda pestaña — no forma parte del Stack de productos. Puede ser tan sencilla como un par de Text con opciones ficticias (“Notificaciones”, “Cuenta”…).

Monta todo con el Tabs de app/(tabs)/_layout.tsx como raíz: una pestaña “productos” que apunta a la carpeta con su propio Stack (lista + detalle), y una pestaña “ajustes” directa.

Reto extra: añade un botón “Volver a la lista” en la pantalla de Detalle con <Link href="/productos">Volver</Link> en vez de depender solo del botón de la cabecera — y, si te atreves, añade un segundo segmento dinámico: una pantalla editar.tsx dentro de [id]/ (ruta /productos/:id/editar) con un formulario simple que, de momento, solo muestre por consola los datos que escribas.

Con esto se cierra el arranque de Bloque 4: de un proyecto vacío a una app con varias pantallas de verdad, navegación y gestos incluidos. Siguiente sesión: entrada de usuario avanzada — formularios más completos, teclados, validación y otros inputs táctiles.
