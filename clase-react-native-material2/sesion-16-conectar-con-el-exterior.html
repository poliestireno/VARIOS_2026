Conectar con el exterior

La app deja de vivir sola en el móvil: hoy pide datos a una API real por internet con fetch, gestiona los estados de carga y error como es debido, y muestra el resultado en una FlatList.

2 horas Sesión 16/26 fetch · useEffect · FlatList

Punto de partida

Todo lo que habéis mostrado en pantalla hasta ahora vivía en el propio código o en el estado del componente. Una app de verdad casi siempre necesita datos que no controla ella: el tiempo, una lista de productos, mensajes de otro usuario. Hoy vais a pedirlos por internet igual que lo haría una página web —porque, de hecho, es exactamente lo mismo— y vais a aprender el patrón que se repite en cualquier pantalla que carga datos remotos: cargando, error o datos.

1 · fetch funciona igual que en la web

React Native no tiene una API propia para peticiones de red: usa la misma fetch del navegador, disponible globalmente sin importar nada. Si ya la usaste en JavaScript web, no hay nada nuevo que aprender en la sintaxis.

const respuesta = await fetch('https://jsonplaceholder.typicode.com/posts');
const datos = await respuesta.json();
console.log(datos); // array de posts

Dos detalles que se olvidan fácil: fetch solo rechaza la promesa (entra en el catch) cuando hay un fallo de red real —sin conexión, DNS caído, timeout. Si el servidor responde con un error 404 o 500, fetch lo trata como una respuesta “normal”, así que hay que comprobar respuesta.ok a mano.

const respuesta = await fetch(url);
if (!respuesta.ok) {
  throw new Error(`Error del servidor: ${respuesta.status}`);
}
const datos = await respuesta.json();

2 · El patrón loading / error / data

Cargar datos remotos siempre pasa por tres estados posibles, y una pantalla bien hecha los representa todos: mientras espera la respuesta, si algo falla, y cuando por fin hay datos que mostrar. Se modela con tres useState y se dispara desde useEffect al montar el componente.

import { useState, useEffect } from 'react';

type Post = { id: number; title: string; body: string };

export default function ListaPosts() {
  const [posts, setPosts] = useState<Post[]>([]);
  const [cargando, setCargando] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    let activo = true;

    async function cargarPosts() {
      try {
        setCargando(true);
        setError(null);
        const respuesta = await fetch('https://jsonplaceholder.typicode.com/posts');
        if (!respuesta.ok) throw new Error('Error del servidor');
        const datos = await respuesta.json();
        if (activo) setPosts(datos);
      } catch (err) {
        if (activo) setError('No se pudo cargar. Revisa tu conexión.');
      } finally {
        if (activo) setCargando(false);
      }
    }

    cargarPosts();
    return () => { activo = false; };
  }, []);

  // aquí abajo: renderizado según cargando / error / posts
}

La variable activo con su “función de limpieza” en el return del efecto no es decoración: evita el error clásico de intentar actualizar el estado de un componente que ya se desmontó (por ejemplo, si el usuario navega a otra pantalla antes de que la respuesta llegue).

Fíjate en que respuesta.json() devuelve Promise<any> — TypeScript no puede saber qué forma tiene lo que llega de una API externa, así que setPosts(datos) compila aunque datos no tenga ni id ni title. El tipo Post te protege a partir de ahí (en el FlatList de abajo, por ejemplo), pero no valida lo que realmente respondió el servidor.

3 · Mostrarlo con FlatList

En la sesión 13 ya usasteis FlatList para listas locales; ahora la fuente de datos es posts, que empieza vacío y se rellena cuando fetch resuelve. El renderizado condicional decide qué pantalla mostrar según en qué estado esté la carga.

import { FlatList, Text, View, ActivityIndicator, StyleSheet } from 'react-native';

if (cargando) {
  return (
    <View style={styles.centro}>
      <ActivityIndicator size="large" />
      <Text>Cargando…</Text>
    </View>
  );
}

if (error) {
  return (
    <View style={styles.centro}>
      <Text>{error}</Text>
    </View>
  );
}

return (
  <FlatList
    data={posts}
    keyExtractor={(item) => item.id.toString()}
    renderItem={({ item }) => (
      <View style={styles.tarjeta}>
        <Text style={styles.titulo}>{item.title}</Text>
      </View>
    )}
  />
);
“Sin conexión” es solo otro mensaje de error

No hace falta detectar la falta de wifi de forma especial: si no hay conexión, fetch rechaza la promesa igual que ante cualquier otro fallo de red, y cae en el mismo catch. Basta con que el mensaje de error sea genérico y claro (“No se pudo cargar. Revisa tu conexión.”) para cubrir ese caso sin código extra.

Práctica: app que consulta una API pública

Vais a construir una pantalla que pida datos a una API pública gratuita, sin necesidad de clave ni registro, y los muestre en una lista con los tres estados bien cubiertos.

1

Elegid la API

Dos opciones sin autenticación, listas para usar directamente:

  • https://jsonplaceholder.typicode.com/posts o /users — datos de prueba genéricos, ideal si queréis una lista de “tarjetas” con título y cuerpo.
  • https://api.open-meteo.com/v1/forecast?latitude=40.4&longitude=-3.7&current_weather=true — el tiempo actual para unas coordenadas, sin clave de API. Cambiad la latitud/longitud a vuestra ciudad.
2

Montad el patrón completo

Tres useState (datos, cargando, error), un useEffect que llama a fetch al montar, y el renderizado condicional de la sección anterior.

3

Lista con FlatList

Si usasteis /posts o /users, renderizad cada elemento como una tarjeta con al menos dos campos (título + cuerpo, o nombre + correo). Si usasteis Open-Meteo, no hay lista —mostrad la temperatura actual y la hora de forma clara, sin FlatList.

Debería funcionar así

Al abrir la app: primero un texto o spinner de “Cargando…”, después la lista con datos reales de internet. Activad el modo avión en el móvil y volved a abrir la app: debe mostrar el mensaje de error, nunca quedarse en blanco ni congelada en “Cargando…” para siempre.

Reto extra

Añadid un botón “Reintentar” que vuelva a lanzar la petición sin recargar toda la app —solo hace falta volver a llamar a la función que hace el fetch, no reescribir el efecto entero.

Si tenéis tiempo: usad TextInput (sesión 15) para que el usuario escriba un ID de post o el nombre de una ciudad, y la petición use ese valor en la URL en vez de uno fijo.
