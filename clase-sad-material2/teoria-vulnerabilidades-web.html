01

Por qué importan estas dos

La inyección SQL y el XSS llevan años entre las vulnerabilidades web más explotadas en el mundo real (top del OWASP Top 10). Comparten la misma raíz: una aplicación que confía en la entrada del usuario y la trata como si fuera código o datos seguros, en vez de tratarla siempre como texto potencialmente hostil.

02

Qué es una inyección SQL

Una inyección SQL (SQL Injection) ocurre cuando una aplicación construye una consulta SQL concatenando directamente el texto que introduce el usuario, sin separarlo del código de la consulta. Si el usuario introduce fragmentos de SQL válido dentro de ese texto, puede alterar el significado de la consulta original.

query = "SELECT * FROM users WHERE user='" + usuario + "' AND pass='" + password + "'"

Esta línea parece inofensiva mientras usuario y password sean texto normal — pero el usuario controla ese texto por completo.

03

Cómo se explota

Si en el campo “usuario” se introduce ' OR 1=1 --, la consulta anterior queda así:

SELECT * FROM users WHERE user='' OR 1=1 -- ' AND pass='...'

La comilla simple cierra el valor que esperaba la consulta; OR 1=1 es una condición siempre verdadera, así que la cláusula WHERE selecciona todas las filas de la tabla; y -- comenta el resto de la línea, anulando la comprobación de la contraseña. El resultado: la aplicación cree que la autenticación ha sido correcta sin conocer ninguna contraseña real. Otro payload habitual con el mismo efecto: admin' --, que autentica directamente como admin ignorando su contraseña.

04

Cómo se corrige: consultas preparadas

La solución no es “filtrar comillas” a mano — es separar por completo el código SQL de los datos, usando consultas preparadas (parametrizadas). El motor de base de datos recibe la consulta con huecos (?) y, por separado, los valores que deben ir en cada hueco — nunca se interpretan como código, pase lo que pase dentro de ellos.

cursor.execute("SELECT * FROM users WHERE user=? AND pass=?", (usuario, password))

Con esta consulta, introducir ' OR 1=1 -- como usuario simplemente busca un usuario cuyo nombre literal sea esa cadena de texto rarísima — que no existe. La inyección deja de tener efecto.

05

Qué es el XSS

Cross-Site Scripting (XSS) ocurre cuando una aplicación web muestra en pantalla, sin ningún tratamiento, texto que proviene del usuario — y ese texto puede incluir HTML o JavaScript, que el navegador ejecutará como si fuera parte legítima de la página.

06

XSS reflejado

El payload viaja en la propia petición — típicamente en un parámetro de la URL — y el servidor lo devuelve (lo “refleja”) directamente en la respuesta, sin guardarlo en ningún sitio. Solo afecta a quien hace clic en un enlace manipulado.

http://tu_servidor/search.php?q=<script>alert('XSS')</script>

Si search.php imprime el valor de q tal cual en el HTML de respuesta, el navegador de la víctima ejecuta ese <script> como si formara parte legítima de la página.

07

XSS persistente (almacenado)

El payload se guarda en el servidor — por ejemplo, en un comentario de un formulario — y se ejecuta automáticamente cada vez que cualquier visitante carga la página donde se muestra ese comentario. Es más peligroso que el reflejado precisamente porque no depende de que la víctima haga clic en un enlace concreto: basta con visitar la página normalmente.

08

Cómo se corrige: codificación de salida

La regla general: cualquier dato que provenga del usuario debe codificarse en el momento de mostrarlo en HTML, convirtiendo los caracteres especiales (<, >, &, comillas) en sus entidades HTML equivalentes, para que el navegador los muestre como texto literal en vez de interpretarlos como etiquetas.

echo htmlspecialchars($_GET['q'], ENT_QUOTES, 'UTF-8');

Con esta codificación, <script> se convierte en el texto literal &lt;script&gt;, que el navegador muestra en pantalla sin ejecutarlo. La misma idea aplica al XSS persistente: el dato se guarda tal cual en la base de datos, pero se codifica siempre en el momento de imprimirlo — nunca al guardarlo.

Un mismo principio, dos vulnerabilidades

SQL Injection y XSS son, en el fondo, el mismo error visto desde dos ángulos: mezclar datos con código (SQL en un caso, HTML/JavaScript en el otro). La solución también comparte principio: separar siempre los datos del código, en vez de confiar en filtrar caracteres “peligrosos” a mano.
