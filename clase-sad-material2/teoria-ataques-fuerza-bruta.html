01

Recordatorio: diccionario vs. fuerza bruta

Un ataque por diccionario prueba una lista concreta de palabras (un fichero de texto, una por línea) contra el campo de contraseña. Un ataque por fuerza bruta prueba todas las combinaciones posibles de caracteres. En la práctica se suele empezar por diccionario — es mucho más rápido — y recurrir a fuerza bruta solo si no funciona.

02

Pydictor

Pydictor es una herramienta escrita en Python que genera diccionarios de palabras para ataques de fuerza bruta. Sus rasgos principales:

  • Genera listas de palabras tanto en texto plano como en distintos formatos cifrados (por ejemplo, base64).
  • Permite construir el diccionario a partir de reglas — longitud, conjunto de caracteres (números, mayúsculas, minúsculas, símbolos), o combinaciones concretas.
$ git clone https://github.com/LandGrey/pydictor.git
$ cd pydictor
$ python3 pydictor.py --len 4 6 -char 1 numbers -o numeros.txt
# diccionario de solo números, entre 4 y 6 dígitos

$ python3 pydictor.py --len 4 6 -char 1 upper -o mayusculas.txt
# diccionario de palabras en mayúsculas, entre 4 y 6 letras
03

Dymerge

Dymerge (incluida junto a Pydictor) fusiona varios diccionarios en uno solo, eliminando duplicados.

$ python3 dymerge.py numeros.txt mayusculas.txt -o diccionarion.txt
# fusiona los dos diccionarios en uno solo, sin repetidos
04

Hydra

Hydra (THC-Hydra) es una herramienta de fuerza bruta contra servicios de autenticación en red — SSH, FTP, HTTP, bases de datos, y muchos más protocolos mediante módulos. Su forma general:

$ hydra -l <usuario> -P <diccionario> <objetivo> <servicio>
# -l: un único usuario fijo — -L: fichero con varios usuarios
# -P: fichero de contraseñas — -p: una única contraseña fija
Solo en tu propio laboratorio

Hydra solo se debe usar contra máquinas y servicios propios, montados para practicar — nunca contra un sistema de terceros sin autorización explícita. Todo este desafío se ejecuta dentro de Kali Purple, contra servicios instalados en la propia máquina.

05

Ataque contra SSH

Pasos para montar el laboratorio y lanzar el ataque:

$ sudo apt install openssh-server
$ sudo systemctl enable --now ssh
# instala e inicia el servidor SSH

$ sudo useradd -m objetivo
$ sudo passwd objetivo
# crea el usuario que hará de víctima de la prueba

$ ssh objetivo@127.0.0.1
# comprueba que el servicio responde y aceptas la clave del host

$ hydra -l objetivo -P diccionarion.txt ssh://127.0.0.1
# ataque de fuerza bruta contra el servicio SSH local

Los intentos de conexión quedan registrados en los logs del sistema (/var/log/auth.log en Debian/Ubuntu, o vía journalctl -u ssh). Revisarlos permite ver, desde el lado defensivo, cómo se detecta un ataque de este tipo en marcha: muchos intentos fallidos seguidos, desde la misma IP, en muy poco tiempo.

06

Ataque contra un formulario web (DVWA)

DVWA (Damn Vulnerable Web Application) es una aplicación PHP/MySQL deliberadamente vulnerable, pensada para practicar. Se instala sobre un servidor Apache local.

$ git clone https://github.com/digininja/DVWA.git /var/www/html/dvwa
# copia DVWA dentro del directorio raíz de Apache
# configura config/config.inc.php con los datos de la base de datos
# entra desde el navegador y pulsa "Create / Reset Database"

Antes de atacar el formulario de login, hay que identificar sus detalles inspeccionando el HTML (nombre de los campos de usuario y contraseña, método del formulario, y el texto que aparece cuando el login falla — Hydra lo necesita para saber cuándo un intento no ha funcionado):

$ hydra -l admin -P diccionarion.txt 127.0.0.1 http-post-form \
  "/dvwa/login.php:username=^USER^&password=^PASS^&Login=Login:Login failed"
# ^USER^ y ^PASS^ son sustituidos por Hydra en cada intento
# el texto final es la cadena que identifica un login fallido
07

Cómo mitigar estos ataques

  • Bloqueo de cuenta o IP tras varios intentos fallidos (por ejemplo con fail2ban en SSH).
  • Limitación de tasa (rate limiting) en el formulario o en el propio servicio.
  • CAPTCHA en formularios web tras varios intentos.
  • Verificación en dos pasos (2FA), que vuelve inútil una contraseña adivinada por sí sola.
  • Política de contraseñas fuertes: longitud mínima, complejidad, sin reutilizar contraseñas filtradas.
  • Desactivar el login directo de root por SSH y usar autenticación por clave pública en vez de contraseña siempre que sea posible.
